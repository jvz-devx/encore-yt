# Integration facts and design

Read this before touching sign-in, playback or the build. Update it when a fact is disproven or a technical choice is made. Facts are dated because YouTube changes.

## Verified facts

- **Toolchain:** Rust 1.98 (ZapFast and Spotifast declare `rust-version = "1.98"`), CMake and a C compiler for the build; at runtime `mpv`, `yt-dlp`, `deno` (yt-dlp's runtime for YouTube's JS challenges) and `secret-tool` (libsecret).
- **Chromium cookie decryption on Linux** (checked 2026-09-30 with Brave Origin 153 and Google Chrome, both using `--password-store=gnome-libsecret`): password = `secret-tool lookup application <brave|chrome|chromium>` with the trailing newline stripped. Key = PBKDF2-HMAC-SHA1(password, `saltysalt`, 1 iteration, 16 bytes); AES-128-CBC with an IV of 16 spaces over the bytes after the `v11` prefix; then PKCS#7 unpadding. From cookie DB schema version 24 the plaintext starts with SHA-256(`host_key`) (32 bytes); strip it. `Local State`'s `os_crypt.portal.prev_init_success = false` means the portal key provider is not in use. Copy the DB before reading; the browser holds it open.
- **Chromium on KDE** (checked 2026-10-06, Google Chrome 152 on Fedora 43 with Plasma 6): Chrome writes `v11` values with the same scheme, but takes the Safe Storage password from KWallet, not the Secret Service (`secret-tool lookup application chrome` is empty). ytfast reads it over D-Bus: `org.kde.kwalletd6` at `/modules/kwalletd6` (else `org.kde.kwalletd5`), interface `org.kde.KWallet`, `networkWallet()` (here `kdewallet`), `open(wallet, 0, "ytfast")`, `readPassword(handle, "<Name> Keys", "<Name> Safe Storage", "ytfast")`, `close(handle, false, "ytfast")`, with Name `Chrome`, `Chromium` or `Brave` as yt-dlp uses them. Opening the unlocked wallet as `ytfast` didn't prompt here. With that password the Default profile's 12 youtube.com/google.com cookies all decrypted (0 failed). `v10` values use the fixed password `peanuts`. `v12` values come from the xdg-desktop-portal Secret key provider (AES-256-GCM, keyed to the calling app); Chrome only decrypts with it by default, and ytfast leaves such values unread and says so.
- **Firefox cookies** (checked 2026-10-06, Firefox on Fedora 43, `cookies.sqlite` `user_version` 17): `moz_cookies` keeps values in the clear. `host` has the same form as Chromium's `host_key` (`.youtube.com` for domain cookies), `expiry` is in milliseconds (older schemas used seconds), and `originAttributes` is empty for the default container and set for container tabs and partitioned cookies (ytfast reads only the default container). Profiles come from `profiles.ini` (`Path`, `IsRelative`, `Name`), each installation's default from `installs.ini`. The database runs in WAL mode and stays open, so copy `cookies.sqlite` with `cookies.sqlite-wal`. Discovery and the query are checked on a signed-out profile; a signed-in Firefox run is still to do.
- **Cookie file sign-in** (checked 2026-10-06 with a synthetic file of fake values and with a real session exported from Helium on macOS): every `~/.config/ytfast/*cookies*.txt` (Netscape format; `#HttpOnly_` lines are cookies) is a sign-in source like a browser profile, listed as "Cookie file (<name>)" with the id `ytfast/<name>` when it holds a SAPISID. The real file signed in (account menu answered, `browse FEmusic_home` came back `logged_in=1`). It is refused unless owned by the user with no group or other permission bits (a 0644 file gives "… can be read by other users. Run `chmod 600 …`, then Reconnect."). Only youtube.com and google.com lines are read. With fake values the account check answers as an expired session ("The YouTube session in Cookie file has expired"). `yt-dlp --cookies-from-browser X --cookies F` without a URL exits 2 ("You must provide at least one URL") but writes F (mode 0600 with umask 077) with every site's cookies; it reads saved cookies only, never a private window's. On macOS yt-dlp reads Chromium passwords with `security find-generic-password -a <Name> -s "<Name> Safe Storage"` (`chromium:<path>` uses `Chromium`); Helium patches its item to `Helium Storage Key` / account `Helium` (imputnet/helium-macos `change-keychain-name.patch`).
- **yt-dlp needs its challenge solver when signed in** (2026-10-06, Fedora 43, yt-dlp 2026.08.19 from the distribution, which lacks the `yt_dlp_ejs` package): with cookies yt-dlp uses web clients whose signatures and `n` parameter need YouTube's JS challenges solved; without the EJS solver scripts it offers only storyboards ("Requested format is not available"), so ytfast's signed-in resolves fail. With `--remote-components ejs:github` (or `yt-dlp-ejs` installed) the same request gave itag 774 (Opus ~222 kbps, Premium). Signed out, other clients need no solver (251).
- **yt-dlp's own browser import doesn't help:** `--cookies-from-browser brave:<profile>` decrypted 0 cookies ("cannot decrypt v11 cookies: no key found"), and `brave+gnomekeyring` needs the Python `secretstorage` module, which a system yt-dlp may lack. So ytfast decrypts the cookies itself and gives yt-dlp a Netscape cookie file (mode 0600, a fresh copy per run, because yt-dlp rewrites the files it's given).
- **Exported cookies go stale:** YouTube rotates session cookies, and an exported `cookies.txt` is soon rejected ("cookies are no longer valid… rotated in the browser"). Re-read the live store at launch and on auth failure.
- **Premium formats:** with valid cookies yt-dlp offers `774` (webm/Opus ~271 kbps) and `141` (m4a/AAC ~258 kbps). Without them the best is `251` (Opus ~134–160 kbps).
- **InnerTube with SAPISIDHASH works:** `browse FEmusic_home` as `WEB_REMIX` `1.20260923.01.00` with the cookies and `Authorization: SAPISIDHASH <ts>_<sha1("<ts> <SAPISID> https://music.youtube.com")>` returns `logged_in=1` in about a second.
- **Stream resolution is slow:** `yt-dlp` with cookies resolves itag 774 in 4–10 s per track depending on the CPU (deno solving YouTube's JS challenges dominates; a warm in-process `yt_dlp` still takes ~6 s). **Don't force `player_client=web_music`:** it was faster on 2026-09-30, but on 2026-10-01 it needed a GVS PO token ("Missing required Data Sync ID") and yielded only a 360p video stream. yt-dlp's default clients still return 774.
- **The iOS client's direct URLs don't play:** the InnerTube `player` endpoint as `IOS` (no cookies) answers in ~0.12 s with direct URLs up to 251, and a 1 KB range fetch succeeds, but mpv fails on them after the first bytes.
- **accesskit and broken accessibility buses:** some desktops advertise an AT-SPI bus that refuses connections. accesskit_unix's D-Bus thread then panics on an `unwrap`. With `panic = "abort"` that killed the app at launch, so the release profile unwinds; only that thread ends.
- **Streams without yt-dlp** (2026-10-07, details in docs/gpui/RESOLVER.md): signed out, the InnerTube `player` request as `VISIONOS` on www.youtube.com returns plain 251 URLs (no challenges, no PO token) in ~0.09 s, and a 1 KB range fetch answers 206. Without a visitor id it answers `LOGIN_REQUIRED` ("confirm you're not a bot"); with the `visitorData` of a YouTube Music response it works. Signed in, `WEB_CREATOR` with cookies returns `signatureCipher` formats up to 251 (no 774 for the song tried), which the embedded QuickJS solves exactly as yt-dlp's EJS does. `TVHTML5` (7.x and 5.x) answers "The page needs to be reloaded" signed in and out. yt-dlp signed out took 2.2 s (watch page, `visionos`, HLS manifest).
- **Resolve time is yt-dlp's floor** (Dell OptiPlex i5-7500, 2026-10-01): ~3.8–4.9 s per song whether cold, warm in-process (`yt_dlp.YoutubeDL` reused: ~3.8 s) or batched (3 URLs in one run: 12.5 s). Running three resolves at once takes ~4.9 s wall in total, so throughput scales with parallel runs. `player_skip=webpage[,configs]` saves ~1 s but loses every Premium format. The InnerTube `player` endpoint as `IOS` now returns direct URLs that answer 403 at once (PO token enforced), and `ANDROID_VR` answers `LOGIN_REQUIRED`: there is no direct fast path.
- **Loudness:** the `WEB_REMIX` `player` response carries `playerConfig.audioConfig` with `loudnessDb`, `perceptualLoudnessDb` and `trackAbsoluteLoudnessLkfs` (e.g. −10.86 LKFS for "Get Lucky"), in ~0.16 s. On 2026-10-01 five songs had `perceptualLoudnessDb` = `trackAbsoluteLoudnessLkfs` (−7.55 to −11.71) and `loudnessDb` = that minus `loudnessTargetLkfs` (−7).
- **mpv 0.41 (Arch, 2026-10-01):** `volume-gain` exists (dB, −150…150) and works as a `loadfile` per-file option: it applies when that entry starts and reverts when it ends, including the gapless move to an appended entry; a live `set_property volume-gain` during an entry also reverts at its end. `af` takes `@ytfast-eq:lavfi=[volume@pre=volume=-6.0dB,equalizer@b0=f=31:t=o:w=1:g=6.0,…]`; `af-command ytfast-eq g 3.5 equalizer@b0` (and `volume -3dB volume@pre`) changes the running graph without rebuilding it, but `get_property af` keeps showing the string last set. `af-command` on `lavfi-equalizer` (no graph) fails.
- **Like state:** the `WEB_REMIX` `next` response has `playerOverlays…likeButtonRenderer.likeStatus` (`LIKE`/`DISLIKE`/`INDIFFERENT`) for the requested song; its `likeEndpoint` is the `like/like` endpoint with `target.videoId`.
- **Timed lyrics:** `browse` with the lyrics browse id (`MPLY…`, from `next`) as client `ANDROID_MUSIC` `7.21.50`, **without** cookies or SAPISIDHASH (with them: HTTP 400), returns `timedLyricsData`: lines with `lyricLine` and `cueRange.startTimeMilliseconds`/`endTimeMilliseconds` (109 lines for "Get Lucky"). LRCLIB (`https://lrclib.net/api/get|search`, no key) has `syncedLyrics` in LRC form, matched by track name, artist and duration.
- **Most replayed:** the `WEB` client's `next` on `www.youtube.com` (anonymous, ~0.9 s) has `frameworkUpdates…macroMarkersListEntity.markersList` with `markerType: MARKER_TYPE_HEATMAP` and 100 markers (`startMillis`, `durationMillis`, `intensityScoreNormalized`) for a music track.
- **Channels (brand accounts)** (checked 2026-10-07, read-only, on an account with its own channel and one brand account): the account menu's "Switch account" item is `getAccountSwitcherEndpoint`, a plain `GET https://music.youtube.com/getAccountSwitcherEndpoint` with the cookies and SAPISIDHASH that answers JSON behind a `)]}'` prefix. `data.actions[0].getMultiPageMenuAction.menu.multiPageMenuRenderer.sections[0].accountSectionListRenderer.contents[0].accountItemSectionRenderer.contents[].accountItem` lists each channel: `accountName`, `channelHandle`, `accountPhoto` (48 px), `accountByline` (subscribers), `isSelected`, and `serviceEndpoint.selectActiveIdentityEndpoint.supportedTokens` with a `pageIdToken.pageId` for a brand account (none for the account's own channel) and `datasyncIdToken` ("<page id>||<user id>" or "<user id>||"). `isSelected` follows the browser's choice in the switcher, but InnerTube requests act as the account's own channel unless they carry `X-Goog-PageId: <page id>` (with `X-Goog-AuthUser: 0`): with it, `account/account_menu` names the brand channel and Library and Liked music are that channel's (2 vs 25 playlists, 0 vs 100 liked songs here). `POST account/accounts_list` as `WEB_REMIX` (YouTube.js's request) answered only a `selectText`. ytfast sends the header on every signed-in request, plays reported through the app's own `player` ping included. yt-dlp only resolves streams, which don't depend on the channel; it would take the channel as `--extractor-args "youtube:data_sync_id=<datasyncIdToken>"` (it derives `X-Goog-PageId` from it), which ytfast doesn't pass.
- **History and Home moods:** `browse FEmusic_history` returns shelves "Today", "Yesterday", "This week"… (200 rows). Home's header `chipCloudRenderer` holds the mood chips (Energize, Feel good, Workout, Relax, Focus, Party, Commute, Sad, Romance, Sleep, and Podcasts).
- **Account writes** (`WEB_REMIX` with cookies and SAPISIDHASH, probed 2026-10-01 in self-undoing pairs; each change confirmed by refetching): `like/like`, `like/dislike` and `like/removelike` with `{"target": {"videoId"}}` rate a song (a fresh `next` shows the new `likeStatus` at once; `removelike` answers `{}`). The same endpoints with `{"target": {"playlistId"}}` save an album or playlist to the library and remove it; an album is saved by its audio playlist id (`OLAK5uy_…`), which the album page's header gives. `subscription/subscribe` and `subscription/unsubscribe` take `{"channelIds": [id]}` with the id from the artist header's `subscribeButtonRenderer.channelId` (a `UC…` id different from the artist's browse id). `playlist/create` takes `title`, `description`, `privacyStatus` (`PRIVATE`) and optional `videoIds` and returns `playlistId`. `browse/edit_playlist` takes `playlistId` and `actions` and answers `status: STATUS_SUCCEEDED` (HTTP 200 also for a refusal: `STATUS_FAILED` with a toast message): `ACTION_ADD_VIDEO` (`addedVideoId`; the answer's `playlistEditResults[].playlistEditVideoAddedResultData` gives each new entry's `setVideoId`), `ACTION_REMOVE_VIDEO` (`setVideoId`, `removedVideoId`), `ACTION_MOVE_VIDEO_BEFORE` (`setVideoId`, `movedSetVideoIdSuccessor`; without a successor the entry moves to the end), `ACTION_SET_PLAYLIST_NAME` (`playlistName`), `ACTION_SET_PLAYLIST_DESCRIPTION` (`playlistDescription`; `""` clears it). `playlist/delete` takes `playlistId`. Unknown ids answer HTTP 404.
- **Duplicates:** `ACTION_ADD_VIDEO` without `dedupeOption` refuses a song already in the playlist (`STATUS_FAILED`, "This track is already in the playlist"); with `dedupeOption: DEDUPE_OPTION_SKIP` it adds a second copy (the dedupe check is what is skipped). ytfast sends no option and reports the duplicate.
- **Account state on pages** (2026-10-01): song rows carry `menu.menuRenderer.topLevelButtons[].likeButtonRenderer.likeStatus` and `playlistItemData.playlistSetVideoId` (playlist and album rows). An album's or other people's playlist's header (`musicResponsiveHeaderRenderer.buttons`) has a `toggleButtonRenderer` (`BOOKMARK_BORDER`) whose `isToggled` is the library state and whose `defaultServiceEndpoint.likeEndpoint.target.playlistId` is the id to save. The account's own playlists have `musicEditablePlaylistDetailHeaderRenderer` (with `playlistId` and `editHeader.musicPlaylistEditHeaderRenderer`), and their Library cards' menus hold a `playlistEditorEndpoint`. Artist headers (`musicImmersiveHeaderRenderer.subscriptionButton.subscribeButtonRenderer`) have `subscribed` and `channelId`.
- **Account changes show with a delay:** a new playlist is listed in Library after ~1.3 s; playlist edits show on the playlist page within 0.2–1.5 s; a subscription shows on the artist page and in `FEmusic_library_corpus_artists` after 1–3 s. Likes showed at once in the morning of 2026-10-01, but in the afternoon `like/like` answered 200 and then `next` kept saying `INDIFFERENT` (and Liked Music didn't list the song) for 3–24 s, with or without a `player` request first; after `like/removelike`, `next` said `LIKE` and Liked Music listed the song for a while too. `next` and Liked Music can disagree with each other during that time. Reads of the account lag its writes by up to ~25 s, not always the same amount.

## Design

- **Metadata:** ytfast's own InnerTube client (`src/innertube.rs`) and a renderer-family parser (`src/parse.rs`), one path for every surface. rustypipe was not used (it has no Home feed, and a second session layer isn't needed).
- **Sign-in (`src/auth.rs`):** every Chromium-family (password from the Secret Service, else KWallet) and Firefox (or LibreWolf, native or Flatpak) profile with a cookie store, most recently used first (Firefox: the newer of `cookies.sqlite` and its WAL), or the one chosen in Settings (`~/.config/ytfast/settings.json`, `src/settings.rs`); each cookie file `~/.config/ytfast/*cookies*.txt` is one more candidate, ordered by its modification time. The account is confirmed with an account-menu request before the UI says "signed in".
- **Streams (`src/resolver.rs`):** yt-dlp by default (`-f 774/141/251/140/250/249/139`, a per-run 0600 copy of the cookie file). With `YTFAST_RESOLVER=rust`, `src/streams.rs` (InnerTube `player` as VISIONOS signed out or WEB_CREATOR signed in, challenges solved by yt-dlp's EJS scripts in an embedded QuickJS, `src/jsc.rs`) goes first and yt-dlp takes over on any failure or when its stream failed to play; see docs/gpui/RESOLVER.md. Resolves run in parallel at two priorities: playback (the current song, then the next) has two slots of its own and never waits behind speculation; speculation (`PrepareMany` with a page's first songs on screen, `Prepare` when the pointer rests on a song, the song two ahead in the queue) has two more, runs under `nice -n 10`, and keeps a most-likely-first backlog of 8. A song asked for twice shares one run; a playback run nobody waits for any more (the click moved on) is killed. Results are cached until 10 minutes before URL expiry, in memory and in `$XDG_RUNTIME_DIR/ytfast/streams.json` (0600), so a relaunch starts at once; entries resolved without cookies don't count once signed in. Each run logs its time and how long it waited for a slot.
- **Audio (`src/mpv.rs`, `src/backend/`):** an `mpv --idle --no-video --no-config` subprocess over JSON IPC. The current track loads with `replace`; the next track, once resolved, is `append`ed, and the move to playlist position 1 is detected and position 0 removed, so mpv's playlist never holds more than two entries. Per-file `loadfile` options carry the user agent (mpv's `%N%` length quoting: they contain commas), the loudness gain (`volume-gain`) and a start time. Repeat-one uses `loop-file=inf`. A stream error retries once through yt-dlp, then skips with a readable error.
- **Audio engines (`src/player/`):** the backend plays through `player::Player`, one deck with mpv's playlist model (the current and the next file, per-file start, gain and user agent, typed events tagged with the deck's serial). mpv (`src/mpv.rs`) is one engine; with the `rust-audio` cargo feature (the GPUI app) the pure Rust `ytfast-audio` (`gpui/crates/audio`, docs/gpui/AUDIO.md) is the other and the default, through `src/player/rust.rs`. `YTFAST_PLAYER=rust|mpv`, then Settings' Audio player, choose; songs the Rust engine can't play (HE-AAC 139/599, or a failure on that song) play on mpv, logged once per song. Installers still ship mpv.
- **Loudness levelling (`src/backend/sound.rs`):** at each track start (and for the next track while it resolves) the `player` response gives the song's LKFS; its gain is −14 LKFS minus that, at most +3 dB, as the entry's `volume-gain`. The same response's tracking URL reports the play to history. On by default; `Settings.normalize`.
- **Equalizer (`src/equalizer.rs`):** ten octave bands (31 Hz–16 kHz, ±12 dB) with a headroom preamp, as one labelled lavfi graph in `af`; Flat or off removes it. Band edits go to the running graph with `af-command`, and `af` is rewritten once edits stop (600 ms) so a graph mpv rebuilds has the same values; then `Settings.equalizer` is saved.
- **Queue edits (`src/backend/queue.rs`):** play order with entry ids, plus list order for unshuffle. Play next inserts right after the current song; Add to queue after the additions waiting there, before the rest of the list; shuffle keeps the additions in order after the current song. Whenever the song after the current one changes, the entry appended in mpv is dropped and the new next one appended. Edits never fetch autoplay's radio: after Clear (or removing the last upcoming song) Up next stays as left, and autoplay starts the radio when the last song ends, as YouTube Music does. Clear also drops the list's pages and any radio still loading.
- **Session (`src/backend/resume.rs`):** `~/.cache/ytfast/session.json` holds the queue (play order, list order, additions), the current song and position, volume, shuffle, repeat and autoplay; written atomically on pause, track and queue changes, seeks and exit (`Backend` drop), and every 10 s while playing. A launch restores it paused, resolves the current song at once, and Play starts at the saved position.
- **Sleep timer:** after N minutes or at the end of the song; the volume fades over the last 8 s, then playback pauses (end of song: the next song waits at its start) and the volume comes back.
- **Decks (`src/backend/deck.rs`, `src/mpv.rs`):** up to three mpv processes at once. The *main deck* (`Worker::mpv`) always holds the current song, and only its events drive playback (position, pause, end of file, the appended next entry, history reporting, session saves, MPRIS through `Event::Playback`). A *second deck* serves Smooth mixes (cued, then tail, then kept as a spare while the setting is on), and an *audition deck* serves Audition (stopped 2 min after the last one). Every process gets a serial at spawn and tags its events with it; the worker routes each event by serial to the deck's current role, so when decks swap roles nothing is misread: a tail's end-of-file only ends the blend, a cued deck's events are ignored unless it fails, an audition deck's events only start its fade-in or end it. Volumes are computed in one place: the main deck plays at `V·fade·∛(duck·in)`, the tail at `V·fade·∛(duck·out)`, the audition at `V·∛level` (mpv's `volume` is cubic in amplitude, so the shares are amplitudes); a 20 ms clock runs only while something fades. The equalizer's `af` and `af-command`s go to every deck; each file's loudness gain stays its own per-file `volume-gain`.
- **Smooth mixes:** Settings "Blend songs on radios and mixes" (`Settings.mixes`, off by default, 3–12 s, default 6). A change blends when the setting is on, repeat isn't One, the sleep timer isn't waiting for the song's end, and the next entry belongs to a radio or mix (the play request was an `RD…` playlist, which Start radio and album/artist Radio are) or was added by autoplay (entry ids recorded at `Extended`; both saved in session.json). Such a next song is not appended behind the current one: when resolved it is *cued* on the second deck, loaded paused at volume 0. When the main deck's position comes within `min(N, duration/3)` of the end (and more than 0.25 s), the cued deck is unpaused and **becomes the main deck at once**: `current_entry` takes its playlist entry id, and the same bookkeeping as a gapless change runs (`advanced`: generation bump, queue position, `reached`, retry/report flags, format, gain, watch info, prefetch, autoplay, session save), so every stamp refers to the new song from that moment. The old main deck becomes the *tail* and plays out its last seconds. Progress `t` is the incoming song's own position over the blend length (so pause and buffering hold it); amplitudes are `sin(πt/2)` in and `cos(πt/2)` out (equal power). At `t = 1` or the tail's end of file the tail is stopped and kept as the spare, and the song after is resolved again (its resolve was set aside while both decks were busy) and cued. Next during a blend completes it at once (the new song stays); Next before a blend starts the cued song at once at full volume; Previous, seeking, pausing, the sleep timer pausing, Jump to and any new play request also end a blend at once. A change the new song makes on its own during a blend (it ends, fails or is skipped, or mpv moves on to a song appended behind it, e.g. a short Play next on an autoplay continuation) stops the tail first (`stop_tail`), because the next song's position starting again at 0 would otherwise read as the blend starting over. A queue edit, shuffle, the setting or repeat changing re-decides how the next song is queued (dropping a cued song returns its deck to the spare). Albums and other playlists keep the appended gapless model untouched.
- **Audition (`src/backend/audition.rs`, `src/ui/audition.rs`):** holding Alt alone (or the middle button) while the pointer is over a song row, card, search top result or Up next row sends `Command::Audition { track, start }` (the caller's best part: until Stage supplies the most-replayed peak, a third of the way in, or 30 s into songs over 6 minutes); letting go, moving off, Alt with another key (Alt+← is Back) or the window closing sends `Command::EndAudition`. The stream comes from the resolver's speculative path (`Resolver::prepared`: the cache, a run already under way, or `prepare` first in line; never a playback slot); until it plays, `Playback.audition` shows it loading and the row shows a spinner; letting go first drops the wait (a request stamp makes late answers inert). It loads with `start` and its loudness gain on the audition deck at volume 0; when its audio starts, it fades in over 250 ms while the main deck ducks to amplitude 0.2 (−14 dB) over 250 ms, and the row's cover gets a pulsing accent ring. Letting go fades both back and stops the audition. The main song never stops, so it continues where it now is; the queue, play order, session and history are never touched (no play reporting for the audition deck).
- **Queue invariant:** `loadfile replace` empties mpv's playlist, so any record of a track appended behind the current one must be cleared on every `replace`. As a safety net, mpv going idle while a track is believed queued advances the queue.
- **Stamps on asynchronous results:** the current track's generation, a queue epoch, mpv playlist entry ids (per process; events reach the right deck by the process serial), audition request stamps and a page request sequence number. Every late answer is checked against them.
- **Offline:** a song that fails twice is skipped only if YouTube is reachable; otherwise playback waits on it and resumes when a reachability check succeeds.
- **History:** after 10 s of play, GET `playbackTracking.videostatsPlaybackUrl.baseUrl&ver=2&c=WEB_REMIX&cpn=<16 random>` with the same auth headers, from the `WEB_REMIX` `player` response (with cookies) fetched when the song started (fetched then if there is none).
- **Theme:** `fastframe_theme::Catalog` with `DesktopThemes { slug: "ytfast", omarchy_template: BASE_TEMPLATE, presets: false }`. It renders Omarchy's current colours itself and watches for changes, so no hook install is needed. `ytfast reload-themes` exists for a hook.
- **Lyrics (`src/lyrics.rs`):** for the playing song, YouTube Music's timed lyrics (`ANDROID_MUSIC` browse of the `MPLY…` id, no session), else LRCLIB's synced lyrics (`/api/get` by title, first artist, album and length; else `/api/search` with the closest length within ±3 s; `User-Agent: ytfast/<version> (<repo>)`), else YouTube Music's plain lyrics, else LRCLIB's plain ones. Asked for as soon as watch-next names the lyrics page, or 3 s into a song without one. The Lyrics tab highlights by the playback position moved on between backend updates.
- **Recent searches:** the last 20 queries, newest first, in `~/.cache/ytfast/searches.json`, read and written (temporary file, then rename) on the backend runtime.
- **Most replayed (`src/heat.rs`, `src/ui/ridge.rs`):** asked once per song (`Command::Heat`, cached in `App::heat` by video id) with the anonymous `WEB` `next` described above; no session, so nothing about the account is sent. The peak is the hottest marker after the first 5 % of the song (the start always reads hot), widened to the neighbouring markers at 85 % of its heat or more; `Action::JumpToPeak` seeks to that part's start. The ridge is a Catmull-Rom curve through the lightly smoothed markers, drawn as a mesh over the page in a non-interactive area at rest (7 pt) and an interactive one under the pointer (28 pt, seeks on click). Songs without heat show the plain seek line.
- **Derived covers (`src/derived.rs`):** an egui image loader for `ytfast-paint://<shadow>-<accent>-<highlight>/<cover url>` (theme-painted covers: up to 360 px, lightness stretched between its 2nd and 98th percentiles and mapped shadow → accent → highlight, the accent at its own lightness). It takes the bytes the cover loader holds and works on the backend runtime (`spawn_blocking`, two at a time). The painting key is the palette's, so a theme switch asks for new images while the previous palette's stand in until they are made; the old ones are freed once nothing on screen needs them.
- **Colour:** every surface, Now Playing and Stage included, draws in the Omarchy theme's palette; only cover art shows its own colours (Tyler, 2026-10-01, reversing an earlier choice to colour Now Playing and Stage from the cover). Now Playing and Stage always show the real cover, even with theme-painted covers on.
- **Stage (`src/ui/stage.rs`):** replaces the whole window (`App::stage`) with the theme's window colour, the cover and cached text, so a frame costs a few rectangles. The cover flies to and from Now Playing (or the player bar) through the `stage` site in `motion`. `Stage::frame_times` keeps `stable_dt` while Stage is open (E2E `surfaces`).
- **egui:** egui 0.36 on the crmne fork uses `App::ui(&mut self, ui, frame)` and an optional `App::logic`, not `update`.
- **Account changes (`src/account.rs`, `src/backend/account.rs`, `src/ui/account.rs`):** optimistic. The app shows the new state (likes by video id, library state by playlist id, subscriptions by channel id) or edits the cached pages in the frame of the input, then sends `Command::AccountEdit` stamped with an operation number. The backend makes account writes one at a time in the order asked, so a like and a quick unlike, or two moves, reach YouTube Music in order, and logs each write and its answer. The app keeps what YouTube Music last said (fresh pages, watch-next, accepted writes) apart from what it shows: what it shows is the newest write still on its way, else what YouTube Music last said; a refusal falls back to that, with a plain message. Fresh pages and watch-next set the shown state (the queue's and player's copies of a song carry no rating), except that a read contradicting a write still on its way, or one accepted less than 90 s ago, is taken as lagging and ignored; a read that agrees ends that wait. 3 s after a success the affected pages are fetched again. Page edits (add, remove, move, rename, create, delete) are overlays on the affected pages as YouTube Music last sent them, applied again to every copy that arrives while they are in flight or for 90 s after; a refusal redraws those pages without it, then refetches them. A playlist's own songs are its first untitled list; "Suggestions" follow it. Dropping a song onto the last loaded row of a longer playlist loads the next part first, because a move with no successor goes to the end of the whole playlist. The playing song's rating comes from the same `next` request that finds its lyrics. The orchestration lives on `AccountState`, independent of the interface: each call borrows the frontend's page cache, a command sender and the sign-in state (`Host`) and returns `Effects` (pages to fetch again, then messages); the module doc of `src/account.rs` lists which event goes to which call, and the egui app's `impl App` there is thin glue.

## Build

```sh
cargo build --release
cargo fmt --all --check
cargo clippy --all-targets --features e2e -- -D warnings
```

**Parser fixtures:** `tests/parse_fixtures.rs` runs saved signed-out `WEB_REMIX` responses (`tests/fixtures/innertube/`: Home, Explore, a search, an album, an artist, a playlist, a mood page, watch-next, plain and timed lyrics) through `parse` and checks the structure the interface relies on, so a change in YouTube Music's responses fails `cargo test --no-default-features`. `cargo run --example capture_fixtures --no-default-features` refreshes them with ytfast's own client and no cookies; it drops tracking and session data (`responseContext`, `trackingParams`, `visitorData`…), menu entries the parser doesn't read and accessibility labels, keeps six cards or rows per shelf and three lines of lyrics. Captured 2026-10-06 (~0.9 MB).

A release build from clean takes about 5 minutes on a 4-core desktop CPU and a few GB of memory. On a small machine, cap it, for example `systemd-run --user --wait --pipe -q -p MemoryMax=5G --working-directory=$PWD -- cargo build --release -j 4`. If two different Rust toolchains are installed, make sure one rustc builds everything (`E0514` otherwise); a machine-local `.cargo/config.toml` (gitignored) can pin `build.rustc`.

## E2E runs

`scripts/e2e.sh [journey|recovery|offline|theme|showcase|motion|pages|desktop|account|engine|engine-restore]` builds with the `e2e` feature and runs the real app on the desktop with the real account, network, yt-dlp and mpv. `src/e2e.rs` clicks controls by their accessible names (`ui::named`) with synthetic pointer events through egui's own input pipeline, types, presses keys, drags, takes framebuffer screenshots and records measurements. It writes `artifacts/e2e/<UTC>-<scenario>/` (gitignored: account data).

- The driver points only at controls drawn in the same place in two consecutive frames. egui lays out a new popup or modal once before showing it (a sizing pass), at a different place: on 2026-10-01 the sleep timer's "End of song" sat ~200 px higher in that first frame and the equalizer's preset chips 14–26 px off, so clicks aimed there landed on Up next or between chips.
- Test-only hooks exist in e2e builds only: `sabotaged(video_id)` hands the resolver an unreachable URL, `offline()` makes the resolver fail and `Client::reachable` report false, and `Backend::make_cold(video_id)` drops a song's resolved stream (streams saved by earlier runs stay valid for hours, so `engine` makes the rows past the first four cold before its cold click).
- `recovery` runs with a stand-in `HOME` holding a copy of a browser profile whose session cookies were overwritten (an expired sign-in). Its reconnect step swaps in a symlink to the real profile.
- `offline` points every request at a dead proxy (`HTTPS_PROXY=http://127.0.0.1:9`).
- `theme`, `showcase`, `pages` and `surfaces` switch the Omarchy theme to `YTFAST_E2E_LIGHT_THEME` (default "Snow") and back.
- `pages` and `surfaces` play songs (they enter the account's history like any play) and put their recent searches back as they found them; `surfaces` also turns theme-painted covers off again.
- `account` changes the real account and puts it back: it likes and unlikes an unrated song on Daft Punk's "Discovery" (playing it for under 10 s, so no play reaches history), saves and removes that album, subscribes to and unsubscribes from Daft Punk, and creates, fills, reorders, trims, renames and deletes a playlist "ytfast E2E". Each change is confirmed by fetching the account again for up to 90 s (its reads lag). It records `account_before`/`account_after` (saved albums, subscriptions, playlists, the song's rating in watch-next and in Liked Music) and fails if they differ or if a precondition doesn't hold (album saved, artist subscribed, song rated, a leftover "ytfast E2E"). Whatever happened, it then puts back what still differs from the start (the song's rating, the album, the subscription, playlists it made; `put_back` in summary.json) and waits until the account reads as found.
- `showcase` runs with an empty stand-in `HOME` (the real Omarchy theme linked in), so it is signed out and its screenshots hold no account data. The README's pictures come from it.
- `engine` then `engine-restore`, in that order: `engine` ends with a session and writes what the next launch must show to `~/.cache/ytfast/e2e-engine-expected.json`; `engine-restore` checks it and puts back the volume, equalizer and levelling. In e2e builds the backend records what mpv reports (`volume-gain` per track, `af`, the sleep fade) for these scenarios.
- Never run two scenarios at once: each stops any running ytfast.

## Exporting a cookie file (sign-in from another computer)

If the browser you use YouTube Music in is on another computer (a Mac, say), export its session as a Netscape cookie file and put it in `~/.config/ytfast/` with a name containing `cookies` and ending in `.txt` (`cookies.txt`, `browser-cookies.txt`). ytfast lists each such file in **Settings** as "Cookie file (cookies.txt)" next to the browser profiles, and uses it for YouTube Music and for `yt-dlp` like a browser's cookies. It reads only a file's youtube.com and google.com lines, and refuses a file unless it belongs to you and only you can read it (mode `0600`).

YouTube rotates the cookies of a session that stays in use, and a copy of them soon stops working. So export a session that won't be used again:

- **Private window (recommended):** open a private window, sign in to music.youtube.com, export the youtube.com cookies with a cookies.txt extension (yt-dlp suggests "Get cookies.txt LOCALLY" for Chromium browsers and "cookies.txt" for Firefox), then close the private window.
- **With yt-dlp:** `yt-dlp --cookies-from-browser` reads a browser's saved cookies, not a private window's. Use a separate browser profile: sign in to music.youtube.com there, quit the browser, export, and don't open that profile again. yt-dlp ends with "You must provide at least one URL" but writes the file anyway; the file holds every site's cookies from that profile, so delete it on the Mac once copied.

  ```sh
  yt-dlp --cookies-from-browser chrome:"Profile 2" --cookies cookies.txt    # Google Chrome
  yt-dlp --cookies-from-browser brave:"Profile 2" --cookies cookies.txt     # Brave
  yt-dlp --cookies-from-browser safari --cookies cookies.txt                # Safari
  ```

  On macOS yt-dlp asks the Keychain for the browser's "Safe Storage" item (`Chrome Safe Storage`, `Brave Safe Storage`; macOS asks you to allow it). Safari needs no Keychain item, but the terminal needs Full Disk Access. For another Chromium-based browser, give yt-dlp the profile's path: `chromium:"$HOME/Library/Application Support/<browser>/<profile>"`. It then looks for the item `Chromium Safe Storage` (account `Chromium`). Helium (profiles in `~/Library/Application Support/net.imput.helium`) files its key as `Helium Storage Key` (account `Helium`), so add a `Chromium Safe Storage` item with the same password for the export and delete it afterwards (this clashes with a real Chromium install, which has its own item):

  ```sh
  security add-generic-password -a Chromium -s "Chromium Safe Storage" \
    -w "$(security find-generic-password -w -a Helium -s 'Helium Storage Key')"
  yt-dlp --cookies-from-browser chromium:"$HOME/Library/Application Support/net.imput.helium/Profile 2" --cookies cookies.txt
  security delete-generic-password -a Chromium -s "Chromium Safe Storage"
  ```

Copy it to the app's config folder with the right mode, then press Reconnect (or restart the app):

```sh
scp mac:cookies.txt ~/.config/ytfast/cookies.txt
chmod 600 ~/.config/ytfast/cookies.txt
```

When YouTube Music says the session has expired, export a fresh one the same way.

Cookies are never logged or written anywhere readable by other users. To see what ytfast can read from each profile (counts only, no values), run `cargo run --example sign_in --no-default-features`. While it runs, the cookie file that `yt-dlp` needs lives in `$XDG_RUNTIME_DIR/ytfast` with permissions `0600`.
